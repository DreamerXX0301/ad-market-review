# 版本升级与回滚

冒险的梦想家可以从源码运行，也可以使用Docker命名卷安装。更新代码、生成计划或构建镜像都不会自动更新现用实例。当前发行目标为`v0.1.1`；实际版本、完整提交、镜像摘要和检查结果以对应发行记录为准。全新拉镜像安装见[Docker部署](Docker部署.md)。

## 版本与发行内容

每次发行保存Git完整提交、测试结果、镜像仓库摘要、基础镜像摘要和迁移文件SHA。可附`v0.1.1`、`sha-完整提交`标签方便检索，正式运行使用`repository@sha256:...`。标签可能被覆盖；摘要指向固定内容。[Docker镜像摘要说明](https://docs.docker.com/dhi/explore/security-concepts/digests/)

源码包含应用、锁文件、迁移、脚本和公开文档；不包含运行数据库、真实原始行情、数据源密文、主密钥、备份、机器个人路径或`node_modules`。源码包、业务备份和原主密钥分别保管。获取新版源码或镜像不能恢复原数据，新的主密钥也不能解密原密文。

## 源码包与CI

`scripts/package_release.py`只读取指定Git提交的普通文件blob，不读取未提交或未跟踪的工作区内容。要求该提交有与前后端一致的`VERSION`，只接受完整40位提交；示例使用项目虚拟环境中的Python：

```bash
backend/.venv/bin/python scripts/package_release.py \
  --commit 完整40位已审核提交SHA \
  --output /新的独立目录/source-v0.1.1
```

生成`ad-market-review-版本-提交前12位.tar.gz`、`source-manifest.json`和`SHA256SUMS`。manifest记录版本、完整Git SHA、迁移文件SHA、逐文件SHA、包大小及包SHA，不伪造测试结果或镜像发布状态。文件顺序、属主、权限、tar时间和gzip头固定，同一提交在相同Python压缩实现中可复现。SHA清单用于完整性核对，不替代发行者签名或可信下载来源。

若提交包含根运行data、密钥、真实环境文件、依赖或构建产物、私人截图/验收材料、个人主目录路径，工具会**拒绝整个提交**，不会悄悄过滤后称其已审核。`frontend/src/features/data`是数据中心源码，仍会保留；`deploy/.env.example`仅作为可扫描的占位模板允许。工具也不执行该提交中的代码、取数、GitHub发布或Docker命令。需Python3.11以上和Git；正式源码在公开提交完成后才打包，不用历史含运行材料的提交代替。

`.github/workflows/ci.yml`在push、普通pull_request或手动触发时运行检查。权限只有`contents: read`，官方Actions绑定完整提交，checkout不保留认证信息；不用`pull_request_target`、部署密钥或GHCR登录。前端执行锁定安装、格式检查、全部`src/**/*.test.mjs`纯测试与构建；后端使用当前生产Dockerfile的固定Python和已修复SQLite运行库，再用独立`Dockerfile.test`安装锁定测试依赖，执行全部后端与部署、升级、打包专项。

后端测试容器不挂Docker socket、数据卷或Key，关闭网络，只读挂载CI宿主Docker CLI和Compose插件供本地`compose config`检查。CI还审核本次提交并生成本地源码包校验值，**CI自身不创建Release、不上传包、不推镜像、不更新任何运行实例**。人工发行工作流`publish-image.yml`在复用CI成功后，才以最小包写权限上传原生amd64/arm64镜像；该流程仍不部署。完整门禁、平台检查与GHCR公开步骤见[Docker部署](Docker部署.md#维护者发行流程)。本文描述已加入的检查配置，不表示GitHub上已经实际跑绿；首次push后的真实结果以Actions记录为准。单独测试镜像不改变生产Dockerfile的默认runtime阶段。

本仓库的两个Compose入口作用不同：

| 文件 | 用途 | 镜像与worker |
|---|---|---|
| `deploy/compose.yaml` | 本地开发、从源码构建和隔离容器测试 | 可本机构建，原有行为保持 |
| `deploy/docker-compose.yml` | 全新拉镜像安装，可单独下载 | 没有build，默认当前版本标签；必须指定Key文件，worker显式启用 |
| `deploy/compose.release.yaml` | 固定摘要的独立预演和人工切换 | 没有build，必须明确镜像、端口和Key文件路径；worker需要显式启用 |

发行Compose的`SHIXU_IMAGE_REF`不能为空；离线计划工具进一步强制它为带完整SHA256摘要的镜像引用。不能填写`latest`或仅标签。Compose本身只检查必填插值，镜像引用合法性由计划工具及Docker校验。不得用发布文件直接指向现用卷来“试启动”；API启动和init都会检查并执行数据库迁移。

## 全新Docker安装

推荐全新安装使用[独立Docker入口](Docker部署.md#全新安装)，可仅用Docker创建新密钥，无需宿主Python。以下是使用严格发行Compose的固定摘要模板，**先替换实际发行镜像摘要**；迁移原数据必须使用原密钥，不能运行创建命令覆盖它。

```bash
python3 deploy/create_secret.py "$HOME/.local/share/shixu-release-secret/master.key"
export SHIXU_MASTER_KEY_FILE="$HOME/.local/share/shixu-release-secret/master.key"
export SHIXU_IMAGE_REF='实际镜像仓库@sha256:发行说明中的64位摘要'
export SHIXU_HTTP_PORT=8789

docker compose -p shixu-v010 -f deploy/compose.release.yaml config
docker compose -p shixu-v010 -f deploy/compose.release.yaml pull
docker compose -p shixu-v010 -f deploy/compose.release.yaml up -d --no-build api
```

确认`http://127.0.0.1:8789/health`、前端和数据源配置均正常后，再明确启动唯一worker：

```bash
docker compose -p shixu-v010 -f deploy/compose.release.yaml --profile worker up -d --no-build worker
```

`up -d api`只运行init和API，不启动worker。无`worker` profile的默认`up -d`也不启动worker。端口只绑定本机；已有8788实例可继续使用，不能让新安装和旧安装引用相同business、published或work卷。首次初始化和盘后增量仍由用户手动发起。

API的published挂载只读，worker独占活动work卷。发行Compose给API一个**独立、可丢弃的work tmpfs**，用于该API进程的指标摘要，不挂载worker的DuckDB、锁或活动文件。它不会跨容器重启保存，也不能复用worker预热的磁盘摘要；宿主直接运行时共享同一work路径的表现与此不同。不要为追求热缓存而把整个worker work卷挂到API。共享独立派生缓存卷属于后续可单独设计的能力。

## 生成离线升级计划

工具只生成`plan.json`、逐阶段说明和四份环境文件，不连接Docker、不读业务库或主密钥正文、不拉镜像、不停止服务、不执行迁移，也不触发同步。计划文件只保存主密钥的**路径**。它针对Compose命名卷安装；当前如果是宿主`dev.sh`运行实例，应按下一节的本机流程处理，不能照搬Docker停止命令。

```bash
python3 scripts/prepare_upgrade.py \
  --current-project shixu-v009 \
  --candidate-project shixu-v010-preview \
  --target-project shixu-v010-final \
  --rollback-project shixu-v009-recovery \
  --current-image '旧镜像仓库@sha256:旧版64位摘要' \
  --candidate-image '新版镜像仓库@sha256:新版64位摘要' \
  --candidate-commit '新版完整40位Git提交' \
  --backup-root /独立磁盘/shixu-upgrade-backups \
  --master-key-file /独立密钥目录/master.key \
  --output /独立目录/shixu-upgrade-plan \
  --candidate-port 8789 --live-port 8788
```

模板中的中文占位符不能直接执行；工具会拒绝无效镜像或提交。四个项目名必须不同，输出目录必须尚不存在，计划与备份目录不能互嵌，主密钥不能放在其中。计划目录0700、文件0600。工具不会验证端口占用、实际卷标签、镜像是否已在本机、发行提交和镜像是否匹配或Key是否能解密，这些在人工执行前核对。

生成的Compose命令显式清除影响镜像、端口与Key路径的旧shell变量，再使用相应`--env-file`，避免交互终端遗留export覆盖已审阅计划。Compose规定shell变量优先于环境文件，所以手写命令也需要核对最终`config`。[Docker插值优先级](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)

不要整份复制执行计划。它包含互斥的正常切换和故障回滚分支，每项有人工前置条件：

1. **预演**：旧8788保持运行，等待当前同步和凭据修改空闲；制作预演备份，校验并恢复到全新预演卷，使用新版摘要启动预演API。迁移只改恢复副本，不启动预演worker；通过只读检查核对业务数量、策略版本、数据日期、来源SHA和原Key解密。不要在预演页新增选股、研究、跟踪或同步。
2. **切换前维护窗**：人工停止旧API和唯一worker，确认没有其他写入者，制作最终备份。该备份包含预演期间用户的新操作，不能用较早预演备份替代。原Key继续独立保存。
3. **正式新版副本**：将最终备份恢复至另一套全新项目卷。新版init/API只迁移此副本，核验后切换本机服务端口；最后明确启动唯一新版worker。备份恢复会把queued/running任务改成paused，是否继续由用户决定。
4. **保留旧版**：保留旧镜像、原数据卷、切换前备份、发行记录及Key。不要执行`down -v`、卷清理或自动清理旧镜像。旧API/worker保持停止，不能两个版本同写一套库。

预演可以不影响旧实例，但最终切换存在维护窗；当前没有透明零停机数据库迁移或跨库双写方案。`/health`仅表示进程可用，不能代替业务验收。

## 数据与迁移保护

现有备份使用SQLite Online Backup API，并锁定已发布不可变文件引用。逐文件校验SHA和公开补充证据链，复制期间补充指针变化则拒绝，不产生假成功包。密文只复制`*.enc`，不读取或复制主密钥；顶层原始下载、活动DuckDB和可重算派生缓存不在标准备份中。[SQLite Online Backup API](https://www.sqlite.org/backup.html)

迁移文件按SHA登记。已执行的文件不能改写，只能新增后续迁移。迁移锁防止同一库多进程同时执行迁移，**不代表新版schema可被旧代码安全读取**。worker的文件锁依赖同一work目录；如果两份容器用了不同work却共享business，锁不能阻止这种错误部署。因此应从项目、卷和维护窗口三层排除共写。

新板块尾部增量的完整原始链、accepted指针和批次摘要位于published补充命名空间，随标准备份一起保存；旧历史缺口不会被每日增量造为完整。首次与盘后批量完成后会预热可丢弃的D/W/M指标摘要，源SHA仍会逐次复验。派生缓存写盘失败只提示，原始板块采集覆盖不被改判失败。

## 回滚

如果只有代码变化且尚未切入新版写入，可以停止新版副本并恢复旧服务，但仍须核对端口和唯一worker。**一旦新版迁移过数据库，不把旧镜像直接挂新版业务库**。

可靠的schema回滚路径是：停止新版API和worker → 使用切换前最终备份恢复到第三套全新卷 → 配原主密钥和旧版固定摘要 → 只启动旧API核对 → 明确启动唯一旧worker。新版卷保留，不合并、不覆盖；它可能包含切换后的新操作，需要单独核对或导出。

此路径的恢复点是最终备份时刻。切换后的选股、研究、跟踪、策略修改或行情增量**不会自动迁回**；回滚前应先保留新版现场，并明确接受或处理这些差异。也不要将一个已使用新版迁移的备份恢复后当作旧schema备份。

## 本机源码运行实例

使用一个新的版本目录或Git worktree安装锁定依赖并构建，旧8788进程继续使用原目录。预演使用备份恢复的独立`SHIXU_DATA_DIR`，显式配置新SQLite、published、raw、work、credentials路径，使用原主密钥；不要遗留环境变量使副本串回原库。只启动临时端口API，不启动worker；API启动会迁移副本。

正式切换仍需维护窗：停止旧API/worker、最终备份、恢复到独立新版目录、指定新版所有路径、迁移验证、启动唯一新版进程。不要在仍有运行进程引用的目录原地`git pull`、运行迁移或用`dev.sh`再起第二worker。此轮只提供Docker离线计划生成，不自动接管宿主进程。

## 复现检查

```bash
backend/.venv/bin/python -m pytest scripts/test_upgrade.py scripts/test_deployment.py -q
```

专项检查使用临时目录和合成路径，验证digest白名单、项目隔离、非法参数、输出不覆盖、无Key读取、候选无worker、回滚顺序及release Compose解析。Compose检查仅执行本地`config`，不启动容器或连接生产库。实际容器/镜像验收仍需独立项目执行原`validate_container.py`；该旧脚本针对开发Compose，并不等于已经演练过真实生产升级。
