# 部署与运维

冒险的梦想家提供本机源码和 Docker 两种运行方式。API 默认只监听本机，唯一 worker 负责行情写入与任务消费；启动服务不会自动发起初始化或盘后更新。已有安装升级先读[版本升级与回滚](版本升级与回滚.md)，不要在现用目录原地拉取并迁移数据库。

当前[Unreleased](../CHANGELOG.md#unreleased)描述当前源码新增功能，独立拉镜像入口仍固定为已发布的 `v0.1.1`。推送 `master`、源码 CI 通过或本地构建成功均不会更新既有 GHCR 镜像。部署前以完整 Git SHA 和真实镜像摘要确认候选内容；尚未另发镜像时，使用该已审定提交在独立目录构建并验证，不把旧版本标签作为新增功能已交付的证据。

## 本机首次启动

需要 Node.js 22.12+、npm、uv，以及 Python 3.13–3.14。Python 实际加载的 SQLite 必须为 3.51.3 以上或程序认可的官方修复回移版本；升级 duckdb 包不会升级 Python 的 SQLite。程序启动会检查 SQLite 运行库。

在仓库根目录执行：

```bash
./scripts/dev.sh
```

脚本安装锁定的后端依赖、迁移默认业务库、构建前端，再启动 API 和一个 worker。浏览器访问 <http://127.0.0.1:8788>；Ctrl+C 停止本次启动的进程。它用于首次安装或开发，不用于现用版本的无感升级。依赖已有变更时先在前端运行 `npm ci`。

启动服务可以消费此前已授权的排队任务，或恢复符合条件的中断任务；不会自行创建新一天的行情同步。手动初始化 / 增量开始后，冻结计划内的分类、板块、补充及本地提醒检查可自动衔接。显式暂停 / 取消仍由用户决定是否继续，不等于开了每日定时任务。

独立调试：

```bash
cd backend
uv sync --frozen
.venv/bin/python -m app.cli migrate
.venv/bin/python -m app.worker
```

另一个终端在 backend 目录启动 API：

```bash
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8788 --workers 1
```

前端构建需在 frontend 目录执行 `npm ci`、`npm run build`。设置数据源并手动初始化的顺序见 [README](../README.md)。不要对同一 data 目录启动第二个 worker。

## Docker 从源码构建

直接拉取发行镜像的推荐安装方式见 [Docker部署](Docker部署.md)。以下用于开发者自行构建：

`deploy/Dockerfile` 使用固定摘要的 Node/Python/uv 镜像、锁定依赖与经 SHA3 校验的 SQLite 源码。当前镜像内要求实际加载 SQLite 3.54.1。支持显式替换镜像来源，但发行记录仍应保留固定摘要。

以下命令只用于全新独立实例，不能用来覆盖已有安装：

```bash
python3 deploy/create_secret.py "$HOME/.local/share/shixu-compose-secret/master.key"
export SHIXU_MASTER_KEY_FILE="$HOME/.local/share/shixu-compose-secret/master.key"
docker compose -p ad-market-review-new -f deploy/compose.yaml config
docker compose -p ad-market-review-new -f deploy/compose.yaml build
docker compose -p ad-market-review-new -f deploy/compose.yaml up -d
```

`deploy/compose.yaml` 是源码开发入口，默认 `up -d` 会启动 API 和唯一 worker；`deploy/docker-compose.yml` 与 `deploy/compose.release.yaml` 则要求显式启用 worker。已有数据的候选预演不能直接套用上面的全新安装命令；按升级文档使用恢复副本，先仅启动候选 API。

源码构建默认使用 `shixu-workbench:local`，`VCS_REF` 默认为 `unknown`。需要交接本地候选镜像时，在干净的已审定提交上构建并传入 `APP_VERSION`、`VCS_REF` 和 `BUILD_DATE`，再记录镜像 ID；这些参数分别来自根 `VERSION`、完整提交 SHA 和该提交时间。只有实际上传仓库并核验后才有可交接的仓库摘要，本地构建不能冒充 GHCR 发行完成。

主密钥父目录必须是 0700；创建脚本拒绝覆盖旧密钥。文件型 Compose secret 以 0444 供非 root 容器读取，宿主其他用户不能遍历其 0700 父目录。不要把密钥正文放进 Git、镜像或环境文件；密文与主密钥必须分开保管。已有密文需原主密钥才能解密。

默认只绑定 `127.0.0.1:8788`；新实例可设置 `SHIXU_HTTP_PORT=8789`。检查与停止：

```bash
docker compose -p ad-market-review-new -f deploy/compose.yaml ps
docker compose -p ad-market-review-new -f deploy/compose.yaml logs --tail 100 api worker
docker compose -p ad-market-review-new -f deploy/compose.yaml down
```

`down` 保留数据卷，日常停止不要加 `-v`。发行用的 `compose.release.yaml` 不构建镜像、要求明确镜像引用，worker 需显式启用；完整步骤见[版本升级与回滚](版本升级与回滚.md)。

## 存储与进程

| 存储 | API | worker | 用途 |
| --- | --- | --- | --- |
| business | 读写 | 读写 | SQLite 业务短事务、WAL 串行写锁 |
| published | 只读 | 读写 | 不可变行情、快照、manifest、已验收补充证据 |
| credentials | 读写密文 | 只读密文 | 来源凭据，不含主密钥 |
| work | 不共享 worker 文件 | 独占读写 | 活动 DuckDB、锁、临时计算 |
| raw | 不挂载 | 读写 | 原始下载与重放材料 |

一次性 init 在新卷中设置权限并迁移，API/worker 以 UID 10001 运行。`/health` 仅代表进程可用，不代表数据完整。API 不得打开另一进程正在写入的 DuckDB。发行配置另给 API 独立 work tmpfs，缓存不跨重启保存。

本机默认数据根为仓库 `data/`。独立版本需显式配置 `SHIXU_DATA_DIR`；必要时同时指定 `SHIXU_SQLITE_PATH`、`SHIXU_PUBLISHED_DIR`、`SHIXU_RAW_DIR`、`SHIXU_WORK_DIR`、`SHIXU_CREDENTIAL_DIR` 与 `SHIXU_CREDENTIAL_MASTER_KEY_FILE`。检查所有覆盖变量，避免副本误连现用库。

## 本机备份与恢复

备份到尚不存在、且位于数据目录之外的路径：

```bash
backend/.venv/bin/python scripts/backup.py --output backups/before-upgrade
```

备份使用 SQLite Online Backup API，固定已发布不可变文件引用，校验 SHA256，复制业务库、被引用行情和凭据密文。盘面补充包含已验收原始证据与指针；复制期间发生变化会拒绝本次备份。备份时等待补充任务结束，避免同时修改来源凭据。

备份不含主密钥、顶层 raw 下载全集、活动 DuckDB 或可重算工作缓存。manifest 校验完整性，不提供防恶意篡改的数字签名。备份目录仍含个人策略与密文，不应公开。

自选、首次加入基准、水平线、已触发提醒和人工上市身份更正属于SQLite业务记录，随业务库保留；`work/`的本地覆盖/缺口报告及`raw/`的额外来源核验响应不在标准备份中。恢复后可重新运行本地核验；需要长期保存额外来源证据时另做私有归档并核对SHA，不将其上传公开仓库。

恢复必须指定尚不存在的新目录：

```bash
backend/.venv/bin/python scripts/restore.py backups/before-upgrade --target /独立路径/shixu-restored
cd backend
SHIXU_DATA_DIR=/独立路径/shixu-restored .venv/bin/python -m app.cli validate
```

先校验清单、大小、hash、SQLite 完整性再恢复；排队/运行任务会暂停，保留已完成结果、策略、人工变更与发布指针。使用原主密钥或重新配置数据源；不要让新旧进程共写恢复目录。

## Docker 卷备份

脚本使用短命 helper 容器，校验 Compose 项目和卷类型标签。下面镜像标签必须是本机已有且已验证的版本；恢复目标项目必须全新：

```bash
backend/.venv/bin/python scripts/docker_archive.py --image shixu-workbench:local backup --project ad-market-review-new --output backups/docker-before-upgrade
backend/.venv/bin/python scripts/docker_archive.py --image shixu-workbench:local restore backups/docker-before-upgrade --new-project ad-market-review-restored
```

恢复不启动服务、不复制主密钥、不覆盖已有卷。验证后再按照升级文档以对应版本启动。不要运行卷清理或删除唯一旧版备份；异盘留存周期由安装者安排。

## 检查与故障处理

- 先看任务阶段、覆盖原因及 API/worker 日志；记录日期、快照 ID 和错误类型，隐藏凭据与个人策略。
- 显式暂停/取消不会自动继续；恢复备份后由用户决定是否恢复旧任务。来源失败不清空已发布版本，不把缺失标成零。
- 迁移文件只允许新增，不改已执行文件；不要把 schema 导出 SQL 当成业务恢复脚本。
- 复现测试、合成数据检查与独立容器检查见[交付与验收](交付与验收.md)。标准升级计划与恢复边界见[版本升级与回滚](版本升级与回滚.md)。

SQLite/WAL 与活动 DuckDB 应使用本地磁盘；当前没有共享网络盘、断电恢复或零停机双写保证。

## 新增功能验收与版本交接

市场温度、下一交易日计划、连板高度与板型反馈这一轮源码改动不新增迁移，当前 schema 为 `023`；这不代表可以绕过独立恢复和切换流程。候选前端、API 与唯一 worker 应来自同一已审定提交，不能仅凭相同的 `0.1.1` 版本字符串判断内容一致。候选 API 的 `/health` 检查应用名、版本与可用性，镜像 OCI revision/发行回执或源码 Git SHA 用于确认实际提交；通过后仍须核对已有业务记录、来源日期与 SHA。

使用独立恢复副本中已留存的数据做以下功能验收，不为验收重新初始化或补造示例数据。研究报告详情读取会续期缓存和保留引用，须单列记录；要求业务记录完全不变的只读对账应排除该读取，不把TTL变化当作无业务变化：

- **市场情绪**：首屏沪深广度温度、阶段、下一交易日计划与页内目录可见；切换盘面日期后不残留上一日计划。日历未知时不猜下一日，缺少报价、覆盖或成交额证据时保留待核验，未来条件均未观察。完整口径及场景见[市场温度与下一交易日计划](市场温度与下一交易日计划.md)。
- **板型与反馈**：总览炸板前五、封单收盘快照、涨停梯队与连板反馈展示有据高度、板型和量能；反馈默认按已核验昨日高度降序，未知高度排后。同股票详情/K线口径一致，缺证据不生成标签。核对[连板高度、板型与次日反馈](连板高度板型与反馈.md)及[个股成交形态标记](个股成交形态标记.md)。
- **原有功能**：已有策略、跟踪、自选、划线、提醒与研究结果仍可读；本轮其他图表和研究阅读入口按[本轮功能验收清单](本轮功能验收清单.md)复核。空数据实例只可确认界面和缺口提示，不能声称真实行情功能验收通过。

向执行升级的人或部署会话交接完整提交、应用版本、迁移范围、检查结果、候选源码包或镜像固定摘要及发行回执，并注明仍待执行的独立恢复验收和正式切换。GHCR 版本发行与回执字段见[Docker部署](Docker部署.md#向部署方交接)；没有新镜像时明确记录“源码已合入、镜像待发行”，保留旧镜像和切换前最终备份。
